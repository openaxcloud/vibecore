## Bug

**P2 — le panneau PROBLÈMES ne s'ouvre jamais, alors que la barre d'état compte bien l'erreur.** Mesuré live le 19/08 sur `e-code.ai` (prod `6fd65b01`), projet réel : la barre d'état affiche « Problèmes 1 0 » et expose un bouton `aria-label="Ouvrir les problèmes : 1 erreur, 0 avertissements."` — le compte est donc JUSTE, le diagnostic remonte. Mais le clic n'ouvre rien : depuis l'éditeur, `?panel=` reste `editor`, aucun `[data-testid="ide-service-panel"]` n'apparaît, et le DOM ne contient AUCUN code d'erreur (`TS####`, `fichier:ligne`). Depuis un autre panneau, le clic bascule sur Shell. L'utilisateur voit donc qu'il a une erreur et n'a aucun moyen de savoir laquelle. À distinguer de BUG-CREATE-002 (déjà corrigé), qui portait sur l'ALIMENTATION du panneau ; ici l'alimentation marche, c'est l'OUVERTURE qui manque.

## Preuve

**Option 2 retenue et validée par Avi : ne PAS toucher à la surface gelée, donner à « Problèmes » son propre panneau.** `'problems'` rejoint `IDE_MANAGEMENT_PANELS` (adresse `?panel=problems`, titre, icône) ; `openBottomTerminal` traite `'problems'` AVANT le repli vers le Terminal, le bureau gardant son tiroir du bas ; les deux surfaces rendent `ProjectProblemsPanel`, alimenté par le store `diagnostics` déjà en place, en court-circuitant `ProjectIdeServicePanel` (dont `/ide-panel/problems` 404erait). Diagnostics cliquables vers `fichier:ligne` conservés. ⚠️ **Le sceau du bloc gelé a refusé ma première version, à juste titre** : le point d'appel mobile vit DANS le bloc scellé par empreinte SHA-256 (`base-chat-ast.spec.ts`). L'aiguillage est donc passé dans une enveloppe SANS crochet définie APRÈS le bloc ; l'empreinte revaut `190c000c…51394`, restaurée octet pour octet. 7 tests dédiés + les 7 du catalogue AST verts. **✅ VOLET MOBILE FERMÉ — certifié en réel le 20/08 sur prod `web:bdaf5af8cc`, aux 3 formats.** **L’hypothèse de départ était FAUSSE, et c’est la mesure qui l’a montrée.** On soupçonnait `setMobileIdePanel('deploy', …)`, appelé en dernier dans la branche mobile de `openBottomTerminal`, d’écraser le `?panel=` posé juste avant. En déclenchant le handler à 390 : `?panel=` passe de `null` à `problems`, `activePanel` à `deploy`, et le panneau s’affiche avec ses 4 avertissements runtime réels — **le routage était correct, rien n’était écrasé**. **Cause réelle : le panneau n’avait AUCUN point d’entrée sous 1200 px.** Son unique déclencheur était la pastille de la barre d’état, masquée par `@media (max-width: 1199px), (max-width: 1366px) and (any-pointer: coarse) { .bolt-project-statusbar-mobile { display: none !important } }`. Mesures : un seul `.bolt-project-statusbar` dans le DOM (classe `…-mobile`), `display: none`, hauteur 0, pastille **0×0** ; et `problems` n’était **ni** dans les 32 outils mobiles **ni** dans le menu Panneaux — la feuille « Ajouter un onglet » listait 33 entrées, **zéro** correspondant à « probl ». Le panneau était donc littéralement inatteignable au doigt, à 390 **comme à 768**. **Preuve indépendante avant correctif** : l’événement applicatif `vibecore:open-project-ide-panel{panel:'problems'}` émis à 390 ne faisait **rien** (`?panel=` restait `null`) — le no-op silencieux que documente l’en-tête de `mobile-ide-tabs.ts` pour un id absent de `MOBILE_TOOL_TO_MANAGEMENT_PANEL`. **Correctif (PR #193, `27742c6d` → merge `bdaf5af8cc`)** : `problems` déclaré comme les autres panneaux de gestion — tuile Outils, entrée Panneaux, et `MOBILE_TOOL_TO_MANAGEMENT_PANEL.problems`. `activateMobileTool` route alors par le chemin générique **déjà prouvé correct**. `openBottomTerminal` n’est pas modifié et la surface Terminal gelée n’est pas touchée. **Pourquoi la suite de tests était VERTE sur un comportement cassé** : le garde-fou `MOBILE_MANAGEMENT_PANELS` de `mobile-ide-tabs.spec.ts` — qui exige que tout panneau soit présent dans les DEUX menus mobiles — **ne listait pas `problems`**. Un panneau absent de cette liste n’est gardé par rien. Il y est ajouté. Contrôle négatif : spec rejoué sans le correctif → **2 échecs**, tous deux nommant `problems` ; avec → **9/9 verts**. **Certification écran après déploiement (`web:bdaf5af8cc`)** — **390** : la feuille passe de 33 à **34** entrées, la tuile « Problèmes / Erreurs et avertissements détectés dans votre espace de travail » s’affiche en français avec son icône ; le clic ferme la feuille, `?panel=` passe `null → problems`, `activePanel → deploy`, et **4 lignes de diagnostic réelles** sont rendues (capture conforme). **768** : tuile présente, `?panel=problems`, **5 lignes**, Shell intact. **1440** : barre d’état bien visible (classe `bolt-project-statusbar` **sans** `-mobile`, `display: flex`), pastille **148×32**, clic → **2 lignes**, Shell intact. *Nuance sur « diagnostics cliquables »* : une ligne ne reçoit son bouton « ouvrir à la ligne » que si son message porte un `chemin:ligne` résolvable dans le projet (`extractProblemLocation` + `resolveProblemWorkbenchPath`). Les diagnostics de ce test sont d’origine **runtime** (avertissements npm, proxy d’aperçu) et n’ont légitimement pas de localisation — ils s’affichent donc en `<li>` non interactifs, par conception et non par défaut. *Défaut cosmétique distinct repéré à 390, non corrigé ici* : dans l’en-tête du panneau, les deux pastilles de comptage se chevauchent (« 0 erreu4s avertissemen »).
