## Bug

**P1 — « clone volt-watt.com » : l'agent répond « je tourne dans WebContainer, aucun accès réseau sortant » et refuse, pendant que ses lanes rapportent « j'ai analysé le site » sur des pages que personne n'a lues (captures d'Avi du 08/09, 08:39, Safari iOS).** Trois causes lues dans le code, pas déduites : (a) les QUATRE prompts (`prompts.ts`, `new-prompt.ts`, `optimized.ts`, `discuss-prompt.ts`) décrivent WebContainer « in-browser, no cloud VM » alors que la prod tourne en `VITE_RUNTIME_MODE=remote-kubernetes` (`infra/cloudbuild/single-web.yaml:29`) : les actions s'exécutent dans un pod `node:24-alpine` + `bash git curl` (`services/workspace-agent/Dockerfile:12`) dont la NetworkPolicy `workspace-controlled-egress` autorise le **443 sortant vers tout Internet public** (`infra/kubernetes/workspaces-runtime/networkpolicies.yaml`) — le refus venait du prompt, pas du réseau ; (b) **aucun chemin ne lisait le site** : le seul fetch web est le widget 🌐 manuel (`WebSearch.client.tsx` → `/api/web-search`, 8 000 caractères de texte, sans CSS ni images), le modèle n'a aucun outil natif (seuls les outils MCP de l'utilisateur, `api.chat.ts` `tools: mcpService.toolsWithoutExecute`) ; (c) le mot « clone » est dans `complexBuildSignals` → orchestration en lanes, qui ne reçoivent que le texte des messages (`buildAgentRunRequestBody`) — d'où les « analyses » inventées. Le `screenshotter` (Playwright) existe mais est verrouillé sur `preview.e-code.ai`.
