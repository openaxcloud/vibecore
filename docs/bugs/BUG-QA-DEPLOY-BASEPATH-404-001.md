## Bug

**✅ RÉSOLU — corrigé sur `main` le 13/08 (`949f0748`), certifié en prod le 20/08 (voir « CERTIFICATION PROD » en fin de preuve).** *Énoncé d’origine :* **P1 — DÉTERMINISTE (2/2) : TOUT déploiement statique marqué `READY` sert une PAGE BLANCHE : tous ses assets renvoient 404 à cause d'un décalage de base path.** Le déploiement se crée et se termine en statut **`READY`**, l'URL publique est présentée à l'utilisateur comme en ligne et le document HTML répond bien **200**. Mais l'`index.html` généré référence ses assets sous le préfixe **`/static-deployments/<deploymentId>/assets/…`** alors que le serveur statique les expose **à la racine** (`/assets/…`). Chaque `<script>`/`<link>` part donc en **404 `STATIC_DEPLOY_FILE_NOT_FOUND`** : le bundle ne se charge jamais, `#root` reste vide, l'utilisateur voit une page blanche. Aucun signal d'erreur : ni le statut du déploiement, ni l'UI ne mentionnent quoi que ce soit.

## Preuve

Déploiement `cmsq9g5s1005x0ndf5in0rbgw` (provider `static`, statut **READY**) sur `https://s-cmsq9g5s1005x0ndf5in0rbgw.preview.34.163.208.161.sslip.io/`. **Document** : `GET /` → **200**, 485 o, `<title>React SaaS</title>`, `<div id="root">`, `<script type="module" crossorigin src="/static-deployments/cmsq9g5s1005x0ndf5in0rbgw/assets/index-tSVnAJOB.js">`. **Assets référencés** : `…/static-deployments/<id>/assets/index-tSVnAJOB.js` → **404** `{"error":"File not found in deployment","code":"STATIC_DEPLOY_FILE_NOT_FOUND"}` ; idem pour le CSS `index-BEH7rByq.css` → **404**. **Preuve du décalage** : les mêmes fichiers répondent **200 à la racine** — `GET /assets/index-tSVnAJOB.js` → **200**, `GET /index.html` → **200** — tandis que `GET /static-deployments/<id>/index.html` → **404**. Les artefacts sont donc bien présents et servis ; **seul le préfixe injecté dans le HTML est faux**. **Piste** : `base` de build positionné à `/static-deployments/<deploymentId>/` alors que l'hôte de déploiement sert depuis `/` (ou préfixe retiré côté proxy pour le document mais pas pour les assets). **Confirmé 2/2 — le défaut est systématique, pas accidentel** : second déploiement `cmsqgpz6i00040nf4vrck0051` (statut **READY**), document `GET /` → **200 / 485 o**, et **ses deux** assets référencés en 404 — `src="/static-deployments/cmsqgpz6i00040nf4vrck0051/assets/index-tSVnAJOB.js"` → **404** et `href="…/assets/index-BEH7rByq.css"` → **404** — alors que les mêmes fichiers répondent **200 à la racine** (`/assets/index-tSVnAJOB.js`, `/assets/index-BEH7rByq.css`). Le préfixe fautif reprend à chaque fois l'id du déploiement courant, donc **aucun déploiement statique ne peut s'afficher**. **IDENTIFIÉ COMME BUG-DEPLOY-LIVE — correctif `57234a22` existant mais NON MERGÉ.** Le commit `57234a22` (« fix(deploy): ne plus prefixer le HTML quand le deploiement a une origine dediee ») décrit **exactement** ce constat, reproduit indépendamment sur le déploiement `cmspyoxst000l0na32v10bj3n` — donc **deux reproductions indépendantes**, la mienne ajoutant le caractère **déterministe (2/2)**. Il vit sur la branche `fix/deploy-static-base-path` et **n'est PAS ancêtre de `origin/main`**. Les images tournant sur l'env d'audit (`api:82603d55f7`, `web:c3636dad2b`) **ne le contiennent pas** — ce qui explique mes 404. **Cause racine (code)** : `rewriteHtmlAbsoluteUrls(original, '/static-deployments/<id>/')` était appliqué **inconditionnellement**, alors que ce préfixe n'a de sens qu'en mode *legacy* par chemin ; avec une **origine dédiée** (`PREVIEW_DOMAIN` défini) le snapshot est servi **à la racine** de `s-<id>.preview.<domaine>`, donc le chemin réécrit est cherché **dans** le snapshot et 404 — exactement ma mesure (assets **200 à la racine**, **404 sous le préfixe**). Correctif : `staticDeployDedicatedOrigin(deploymentId) ? original : rewriteHtmlAbsoluteUrls(...)`. **Effet du correctif VÉRIFIÉ en isolement (12/08)** — le commit embarque `services/api/src/static-deploy-base-path.spec.ts` (112 lignes, 3 cas). Exécuté sur un worktree détaché à `57234a22` : **3/3 verts**. **Contrôle négatif** : le même spec rejoué contre le code **actuel non corrigé** → **1 échec / 2 passés**, l'assertion en échec étant `expect(html).toContain('src="/assets/index-CZ8Vosv_.js"')` avec pour sortie réelle `src="/static-deployments/cmspyoxst000l0na32v10bj3n/assets/index-CZ8Vosv_.js"` — **le préfixe fautif exact**. Le spec échoue donc sans le correctif et passe avec : l'effet est prouvé au niveau unitaire. Le spec couvre aussi la **non-régression du mode legacy** (préfixe conservé quand aucune origine dédiée n'existe) et la copie de l'arbre d'assets. **✅ CORRECTIF VALIDÉ EN RÉEL (12/08) — le 404 disparaît.** Image `api` construite depuis un worktree détaché sur `57234a22` (Cloud Build `b656cfa2`, **SUCCESS**, 6 min 29 s, tag `fix57234a`), déployée sur l'env d'audit par `kubectl set image` (rollout OK, image confirmée sur le Deployment). Nouveau déploiement statique `cmsqoay7u00060n91guhztq2b` → **READY**. **Résultat AVANT / APRÈS sur le même env, même projet** : `src="/static-deployments/<id>/assets/index-tSVnAJOB.js"` → **404** devient `src="/assets/index-tSVnAJOB.js"` → **200** ; le CSS passe de **404** à **200** ; le nombre d'occurrences de `static-deployments` dans le HTML tombe de **2 à 0**. Les deux assets référencés se chargent donc désormais, ce qui élimine la page blanche. **Conclusion : `57234a22` corrige effectivement le défaut, prouvé au niveau unitaire ET en déploiement réel. Il ne reste qu'à le MERGER.** **⚠️ CORRECTION DU CONSTAT « NON MERGÉ » (20/08).** L’affirmation ci-dessus (« `57234a22` … n’est PAS ancêtre de `origin/main` ») était exacte **au moment de la mesure du 12/08** mais a été **périmée dès le lendemain** : le correctif a été reporté sur `main` en **`949f0748`** (date de commit **2026-08-13 13:15 +0300**), copie **rebasée** de `57234a22`. La branche `fix/deploy-static-base-path` est donc **superflue** (1 commit en avance, 369 en retard) et **aucune PR n’était à ouvrir** : il n’y avait ni merge ni déploiement à faire. L’image `api` que testait l’env d’audit (`82603d55f7`) est bien **antérieure** à `949f0748` — ce qui explique les 404 mesurés le 12/08. **✅ CERTIFICATION PROD (20/08) — le défaut ne se reproduit plus.** Prod tourne `api:93ed3c708f` (19/08), qui **contient** `949f0748` (299 commits après) ; `PREVIEW_DOMAIN=preview.e-code.ai` est bien défini dans le ConfigMap prod, donc `staticDeployDedicatedOrigin()` renvoie une origine dédiée et la branche « pas de réécriture » du correctif s’applique. **Déploiement statique réel créé de bout en bout** (compte jetable `qa-basepath-1787226945@local.test`, jamais un compte prod) : projet blank → workspace `ws-66ecbbb21333f833` → écriture des 7 fichiers du starter Vite → `POST /projects/…/deployments` → build réel en pod (`vite v5.4.21`, `✓ 31 modules transformed`, `✓ built in 2.32s`) → déploiement **`cmt1gv371003x0ndiyp2vv45v`** → **`READY`** sur `https://s-cmt1gv371003x0ndiyp2vv45v.preview.e-code.ai/`. **Mesures** : `GET /` → **200**, 401 o, `text/html`.
