## CONCLUSION (COLDSTART-01)
Dominant phase on a WARM node with cached image = started->Ready (app boot +
readinessProbe), ~6-7s, the single largest contributor to the ~10.5s total.
This is driven by the readinessProbe config (initialDelaySeconds:3, periodSeconds:5):
an Express app binds in <1s but the first probe fires at t+3s and, if missed,
the next is at t+8s. TUNABLE (initialDelaySeconds:1, periodSeconds:1-2) — but
per the rule, cause identified BEFORE optimizing; no change applied yet.

Image pull (163MB, UNCACHED) = 1.155s -> NOT a bottleneck (AR same-region).
  => GKE Image Streaming would save ~nothing here; my earlier "Image Streaming
     is the cheap win" claim is REFUTED by measurement.
Sandbox gVisor+volume ~2s. Routing (preview-proxy Ready->200) ~2.2s (variable).
Control-plane+scheduling ~0.3s (negligible).

The earlier "91s" baseline was a BOOT-SCRIPT deploy (npm install at boot) — a
DIFFERENT code path, not the image path. Invalid comparison; retracted.

NOT YET MEASURED (needs a cold NODE, i.e. autoscaler scale-up): the worst-case
first-boot on a fresh node (node provision + image pull on cold node + kubelet).
Blocked on SSD quota headroom (434/500; raise 500->2000 in flight). This is the
variant that historically showed 1-2min and must be measured before any
scale-up optimization.
